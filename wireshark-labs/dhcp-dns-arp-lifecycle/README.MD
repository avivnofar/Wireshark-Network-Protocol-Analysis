# Network Protocol Analysis: DHCP, DNS, and ARP Lifecycle

## 📌 Project Overview
This project demonstrates practical network analysis and troubleshooting techniques by forcing, capturing, and analyzing fundamental network protocols (**DHCP, DNS, and ARP**). By manipulating the Windows network stack via the command line, I generated real-world traffic scenarios to analyze protocol mechanics, packet structures, and state sequences under Wireshark.

## 🛠️ Tools & Methodology
* **Network Analyzer:** Wireshark v4.6.5
* **Operating System:** Windows 11 Environment
* **Diagnostic Tools:** Windows Command Prompt (CMD)

### Test Execution Strategy:
To cleanly capture the protocols without background noise, the local network state was systematically altered using the following commands:
1. `ipconfig /release` - Releases the current lease and drops the IP configuration.
2. `ipconfig /flushdns` - Purges the local DNS resolver cache to guarantee fresh query generation.
3. `ipconfig /renew` - Forces a fresh DHCP allocation sequence.

## 🔍 Detailed Protocol Analysis

### 1. DHCP & The DORA Process
* **Wireshark Filter:** `dhcp` or `bootp`

#### The 2-Way vs. 4-Way Handshake Observation
During testing, an interesting behavior occurred when executing a standard `ipconfig /renew` on an active interface. Instead of a full 4-stage DORA process, the client executed an optimized **2-stage handshake** (Request -> ACK). This happens because the client attempts to fast-track its lease renewal by requesting its previously preferred IP address immediately.

To capture the complete, classic **4-stage DORA process**, I disabled the Wi-Fi adapter entirely and re-enabled it to simulate a cold boot connection.

### 2. DNS Resolution Sequence
* **Wireshark Filter:** `dns`

Following the local cache flush via `ipconfig /flushdns`, a network lookup was triggered using `nslookup google.com` to capture raw domain name resolution.

<p align="center">
  <img src="screenshots/dns_udp_port53.png" width="85%" alt="DNS Packet Details">
  <br>
  <em>Figure 2: DNS Query and Response operating over UDP Port 53.</em>
</p>

**Key Analysis Insights:**
* **Layer 4 Protocol:** The capture confirms that standard DNS resolution runs strictly over **UDP** to minimize overhead and optimize speed.
* **Port Mapping:** The traffic targets destination **Port 53** on the DNS server.
* **Transaction Identification:** The Query and Response packet pairs were validated and tracked via matching unique Transaction IDs generated by the client.
